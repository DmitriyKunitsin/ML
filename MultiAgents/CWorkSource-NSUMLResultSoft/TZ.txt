## Техническое задание: Obsidian Code Knowledge Base Generator v2

### 1. Цель проекта и область применения

Разработать Python‑скрипт, который автоматически создаёт базу знаний в формате Obsidian Vault для произвольного программного проекта. Скрипт рекурсивно сканирует целевой проект, анализирует файлы поддерживаемых языков (Python, JavaScript, TypeScript, Go), извлекает метаинформацию (назначение файла, функции, классы, импорты/зависимости) и генерирует по одному Markdown‑файлу (`.md`) на каждый анализируемый файл. В каждом `.md` файле проставляются Obsidian wiki‑ссылки (`[[Имя_файла]]`) на файлы, от которых данный файл зависит.

Результирующая структура `.md` файлов сохраняется в указанную выходную директорию, которая может быть открыта в Obsidian как готовое хранилище (Vault). При открытии Vault пользователь видит интерактивный граф зависимостей между файлами проекта.

**Область применения:** автоматизация документирования кода, онбординг новых разработчиков, визуализация архитектуры проекта.

### 2. Спецификация окружения

| Параметр | Значение |
|----------|----------|
| **Язык реализации** | Python 3.9+ (интерпретируемый, кроссплатформенный) |
| **Операционные системы** | Windows, Linux, macOS |
| **Тип приложения** | CLI (Command Line Interface) |
| **Парсер аргументов** | `argparse` (позиционный аргумент `input` + именованные `--output`, `--ignore`) |
| **Зависимости** | перечислены в `requirements.txt` (обяз.: `chardet`, только для проекта Obsidian – необязательно; остальные – стандартная библиотека) |
| **Ограничения** | Скрипт не должен использовать внешние компиляторы или линтеры; весь анализ выполняется на основе текстового содержимого файлов. |

#### 2.1 Пакеты и зависимости

```txt
# requirements.txt
chardet>=5.0   # обязателен, определяет кодировку файлов
```

Все остальные зависимости – из стандартной библиотеки Python (`os`, `re`, `ast`, `argparse`, `logging`).

### 3. Требования к коду

#### 3.1 Функциональные требования

1. **Рекурсивный обход директории**  
   - Принимает путь к проекту (аргумент `input`).
   - Обходит все файлы, исключая системные/сборочные каталоги: `.git`, `node_modules`, `venv`, `__pycache__`, `dist`, `build`, `.svn`, `.hg`.
   - Пользователь может дополнительно задать шаблоны для игнорирования через флаг `--ignore` (список глобов, разделённых запятыми).

2. **Фильтрация файлов по расширениям**  
   - Обрабатываются только файлы с расширениями: `.py`, `.js`, `.ts`, `.go`.
   - Файлы других текстовых расширений (`.txt`, `.yml`, `.json`, `.md` и т.д.) игнорируются с записью в лог уровня `DEBUG`.
   - Бинарные файлы (расширения `.exe`, `.bin`, `.jpg`, `.png`, `.zip`, `.tar`, `.gz` и т.п.) также игнорируются. Дополнительно применяется эвристика: при обнаружении нулевого байта (`\x00`) в первых 512 байтах файл считается бинарным и пропускается.

3. **Определение кодировки**  
   - Для каждого текстового файла сначала предпринимается попытка декодирования в `UTF-8`.
   - При ошибке `UnicodeDecodeError` вызывается `chardet.detect()` для чтения первых ~32 КБ. Если `chardet` не установлен – скрипт аварийно завершается с сообщением об ошибке (требование обязательности).
   - Если результат `chardet` даёт кодировку с уверенностью > 0.8 – используется она; иначе – decoding with `utf-8` и заменой ошибочных символов (`errors='replace'`).

4. **Анализ содержимого (языкозависимый)**  
   - **Python**: использование стандартного модуля `ast` для извлечения import'ов (from ... import, import ...), определений функций (`ast.FunctionDef`), классов (`ast.ClassDef`), а также docstring модуля (первый строковый литерал). Для модулей без docstring генерация заглушки "No documentation found".
   - **JavaScript / TypeScript**: простой regex (`/import .* from ['"].*['"]/g`, /function\s+\w+\s*\(/, /class\s+\w+/). Допускается извлечение импортов и деклараций без учёта контекста комментариев и строковых литералов (однако при регене следует избегать ложных срабатываний: для JS/TS в первую очередь искать `import` и `require`).
   - **Go**: regex (`/^import\s+\(?/m`, /func\s+\w+\s*\(/, /type\s+\w+\s+struct/). Обрабатываются методы, но без разделения пакетов.
   - Все извлечённые функции/классы записываются в секцию **Функции / Классы** внутри Markdown.

5. **Генерация Markdown для каждого файла**  
   - Шаблон файла `*.md`:
     ```
     # Имя_файла (без расширения)
     
     **Путь:** `относительный/путь/от/input`
     
     ## Описание
     (docstring/первый комментарий, если найден, иначе "No documentation")
     
     ## Зависимости (импорты)
     - [[Другой_файл]]  (только если файл существует в проекте)
     - module (внешние библиотеки – без скобок)
     
     ## Функции
     - `имя_функции` (строка №)
     - ...
     
     ## Классы
     - `ИмяКласса` (строка №)
     ```
   - Wiki‑ссылки ставятся **только на файлы внутри проекта**, которые также будут сгенерированы. Имя файла для ссылки – относительный путь без корня, с заменой разделителей `/` на `_` (чтобы избежать проблем с путями в Obsidian), **но** с сохранением иерархии папок. *Подробнее в п. 3.1.6.*

6. **Стратегия разрешения коллизий имён файлов**  
   - **Критическая проблема в предыдущем ТЗ**: плоская структура с простой заменой `/` на `_` приводит к коллизиям (например, `src/utils/helper.py` и `src_utils/helper.py` после замены могут совпасть, если в пути есть `src_utils`).  
   - **Решение:** В выходном Vault сохраняется относительная структура папок.  
     - Для файла `project_root/src/utils/helper.py` создаётся файл `vault/src/utils/helper.md`.  
     - Wiki‑ссылка формируется как `[[src/utils/helper]]`. Obsidian поддерживает вложенные папки и ссылки с путями (в Obsidian ссылка `[[src/utils/helper]]` ведёт на файл по адресу `src/utils/helper.md`).  
     - Если же пользователь настаивает на плоской структуре (флаг `--flat`), тогда имя файла формируется так: `src_utils_helper.md`, а вики‑ссылка – `[[src_utils_helper]]`. При наличии коллизий (два разных пути дают один и тот же хэш‑имя) добавляется суффикс `_1`, `_2`, и т.д. (гарантия уникальности).  
   - Без флага `--flat` по умолчанию используется иерархическая структура (подпапки). Этот флаг должен быть явным.  
   - Для избежания дублирования вики‑ссылок без расширения (например, `a.py` и `a.js`): в плоском режиме они будут конфликтовать, поэтому при наличии двух файлов с одинаковым базовым именем, но разным расширением, к имени добавляется суффикс `_py`, `_js` и т.д. В иерархической структуре коллизия исключена, так как пути разные.  

7. **Обработка ошибок**  
   - Невозможность прочитать файл (нет прав) – логируем `WARNING` и пропускаем.  
   - Пустые файлы – создаётся `.md` с минимальным содержанием и пометкой "Empty file".  
   - Слишком большие файлы (более 10 МБ) – пропускаем с предупреждением (настраиваемый лимит `--max-size`).  
   - Ошибки парсинга (например, синтаксическая ошибка в Python при `ast.parse`) – логируем `ERROR` и используем fallback regex (только импорты).  

8. **Интерфейс командной строки**  
   ```
   python code2obsidian.py /path/to/project [--output /path/to/vault] [--ignore *.txt,*.bin] [--flat] [--max-size 10]
   ```
   - Позиционный аргумент `input` – обязательный.  
   - `--output` – необязательный, по умолчанию `./obsidian_vault`.  
   - `--ignore` – шаблоны для исключения (через запятую).  
   - `--flat` – переключает на плоскую структуру (по умолчанию иерархическая).  
   - `--max-size` – размер в МБ, по умолчанию 10.  

#### 3.2 Нефункциональные требования

- **Модульность**: код разделить на модули: `scanner.py` (обход и фильтрация), `parser.py` (анализ каждого файла), `generator.py` (создание .md), `cli.py` (аргументы), `main.py` (точка входа).  
- **Обработка ошибок**: все внешние исключения ловить логгером; скрипт не должен крашиться из-за одного повреждённого файла.  
- **Ограничение по времени**: для проекта до 10 000 файлов общее время генерации не должно превышать 5 минут.  
- **Документация**: docstrings для всех публичных функций (на английском языке), комментарии в сложных местах (можно на русском).  
- **Кодировка исходного кода**: UTF-8.  

### 4. Критерии приемки (Definition of Done)

1. Скрипт обрабатывает указанный проект и создаёт Vault с корректными `.md` файлами.  
2. Для каждого файла проекта (кроме игнорируемых) создан один `.md` файл с описанием, функциями/классами, зависимостями и wiki‑ссылками.  
3. Вики‑ссылки указывают на файлы внутри Vault и кликабельны в Obsidian (граф связей отображается).  
4. Коллизии имён отсутствуют (проверено на тестовом проекте, включающем `src/utils/helper.py` и `lib/helper.py`).  
5. Обрабатываются все поддерживаемые языки (Python, JS, TS, Go).  
6. Бинарные файлы и файлы с неподдерживаемыми расширениями игнорируются (лог `DEBUG`).  
7. При отсутствии `chardet` скрипт завершается с явным сообщением об ошибке.  
8. Тестовый проект (небольшое Flask‑приложение + JS/TS) успешно проходит генерацию без крашей.  
9. Документация кода (docstrings) присутствует в каждом модуле.

| Обработка дубликатов имён без расширения | В иерархическом режиме – не возникает; в плоском – добавляется суффикс языка. |
| Содержимое `.obsidian/app.json` | Минимальная конфигурация `{"showInlineTitle": false}`; на этапе MVP это достаточно. |
| Тестовый проект | Ожидается поддержка смешанных проектов (Python + JS/TS + Go). |
