## Результаты ревью кода

### Найденные баги и замечания

#### **Критические**
- Отсутствуют.

#### **Мажорные**
1. **Несоответствие ТЗ: обработка недоступных для чтения файлов**  
   - Согласно ТЗ (раздел 3.1, п.7): «Невозможность прочитать файл (нет прав) – логируем `WARNING` и пропускаем».  
   - В текущей реализации: в `parse_file` при ошибке `OSError` не пропускает файл, а создаёт `FileMetadata` с docstring «No documentation found» (без отметки об ошибке). При этом в лог пишется только `WARNING`, но `.md` файл генерируется. Это может ввести пользователя в заблуждение (создаётся документация для недоступного файла).  
   - **Рекомендация:** В `parse_file` при `OSError` следует вернуть `None`, а в `main.py` при `None` – не добавлять в `metadata_list` и логировать пропуск.

2. **Коллизия имён в иерархическом режиме для файлов с одинаковым именем и разными расширениями**  
   - ТЗ утверждает: «В иерархической структуре коллизия исключена, так как пути разные».  
   - Однако `_resolve_link_name` для `flat_mode=False` отбрасывает расширение, поэтому `src/utils/helper.py` и `src/utils/helper.js` получат одинаковый `link_name = "src/utils/helper"`. Код решает коллизию добавлением суффикса `_1`, `_2` и т.д., что противоречит заявлению ТЗ. Хотя функционально это работает, отсутствие явного документального соответствия может ввести в заблуждение.  
   - **Рекомендация:** Либо изменить алгоритм, чтобы в иерархическом режиме учитывалось расширение (например, `"src/utils/helper.py"` → `"src/utils/helper_py"`), либо явно указать в документации, что коллизии разрешаются добавлением числового суффикса даже в иерархическом режиме.

#### **Минорные**
1. **Формирование пути в `.md` файле**  
   - В `_generate_md_content` для поля «**Путь:**» используется `fi.relative_path` без нормализации слешей. На Windows это может выдать обратные слеши (`\`), хотя Obsidian и Markdown обычно работают с прямыми.  
   - **Рекомендация:** Использовать `str(fi.relative_path).replace("\\", "/")` для единообразия.

2. **Обработка `stem` в плоском режиме при наличии точек в имени**  
   - В `_resolve_link_name` для `flat_mode=True` применяется `Path(name).stem`, что отбрасывает только последнее расширение. Например, `"src/helper.test.py"` → `"src_helper.test"`, а не `"src_helper_test"`. Хотя коллизий это не создаёт, неочевидно, что точка в середине имени сохраняется.  
   - **Рекомендация:** Возможно, стоит заменять все точки на подчёркивания после замены слэшей, чтобы избежать путаницы.

3. **Регулярные выражения для JS/TS**  
   - Regex `import\s+.*?\s+from\s+['"]([^'"]+)['"]` не обрабатывает такие конструкции как `import 'foo'` (без `from`) и `import('foo')` (динамический импорт). ТЗ допускает простой regex, но потенциально могут теряться некоторые импорты.  
   - **Рекомендация:** Если важна полнота, расширить regex, но в рамках MVP допустимо.

4. **Логирование в `scan_files`**  
   - Для неподдерживаемых расширений (не `.py`, `.js`, `.ts`, `.go`) нет логирования на уровне `DEBUG`, как требует ТЗ (раздел 3.1 п.2). В коде просто `continue`.  
   - **Рекомендация:** Добавить `logger.debug("Ignoring file %s due to unsupported extension", entry)`.

### Сценарии для тестирования

| # | Сценарий | Ожидаемый результат |
|---|----------|---------------------|
| 1 | Пустая входная директория | Создаётся пустой vault (только `.obsidian/app.json`, без `.md` файлов) |
| 2 | Директория с одним Python-файлом без импортов, с docstring | Генерируется `.md` с корректным описанием, секции «Функции/Классы» пусты |
| 3 | Файл с синтаксической ошибкой Python | Используется fallback regex для импортов, функции/классы не выводятся, лог `WARNING` |
| 4 | Бинарный файл (с нулевым байтом в первых 512 байтах) | Пропускается, лог `DEBUG` (если добавить) |
| 5 | Файл с размером > `--max-size` | Пропускается с предупреждением в логе |
| 6 | Файл без прав на чтение (например, `chmod 000`) | Пропускается, логируется `WARNING`, `.md` не создаётся |
| 7 | Плоский режим: два файла с одинаковым именем, но разными расширениями (`helper.py`, `helper.js`) | Генерируются `helper_py.md` и `helper_js.md` (или с суффиксами при коллизиях) |
| 8 | Иерархический режим: файл `src/utils/helper.py` и `src/utils/helper.js` | Должны быть файлы `src/utils/helper.md` и `src/utils/helper_1.md` (согласно текущей реализации) |
| 9 | Игнорирование по паттерну `--ignore *.tmp` | Файлы `.tmp` не обрабатываются |
| 10 | Отсутствие пакета `chardet`, файл не в UTF-8 | Программа завершается с сообщением об ошибке и exit code 1 |
| 11 | Импорт, ссылающийся на существующий в проекте файл | Wiki-ссылка `[[путь/к/файлу]]` появляется в секции «Зависимости» |
| 12 | Импорт внешнего модуля (например, `os`) | Отображается как `os` без скобок |

### Рекомендации по исправлению

1. **В `parser.py`** — изменить обработку `OSError` при открытии файла:  
   Instead of returning `FileMetadata` with empty fields, return `None` and let the caller skip the file.

2. **В `main.py`** — при вызове `parse_file` проверять, не равен ли результат `None`, и если да — логировать `WARNING` и не добавлять в `metadata_list`.

3. **В `generator.py`** — для иерархического режима либо включить расширение в `_resolve_link_name` (например, `rel_stem + "_" + ext_suffix`), либо явно документировать поведение с добавлением числовых суффиксов при коллизиях.

4. **В `_generate_md_content`** — нормализовать путь в строке «**Путь:**» заменой обратных слешей на прямые.

5. **В `scanner.py`** — добавить логирование для файлов с неподдерживаемыми расширениями (уровень `DEBUG`).

6. **В cli.py / parser.py** — если требуется точное соответствие ТЗ по коллизиям, возможно, переработать стратегию, но это выходит за рамки точечных правок.
